# 06_storyboard.json 规范（分镜稿 · 视频叙事）

视频线第一步产物是 `06_storyboard.json`：它决定每镜念什么、画什么、多长。写完先过 R1–R10，再进 TTS。
schema 版本 **1.2**；规则编号 R1–R10（含 R2b/R2c）由本文档定义，任何实现与本文档冲突时以本文档为准。

## 1. Schema

### 顶层字段

| 字段 | 类型 | 必填 | 含义 |
|---|---|---|---|
| `schema_version` | string | 否 | 本文档版本，当前 `"1.0"`；脚本按它选校验口径 |
| `title` | string | 是 | 内部标题，不念、不上屏 |
| `publish_title` | string | 是 | 视频号标题，≤15 个汉字（数字、英文各算半个字） |
| `publish_desc` | string | 是 | 视频号描述，≤20 个汉字，补标题没说完的钩子 |
| `voice` | string | 是 | TTS 音色，默认 `zh-CN-YunxiNeural`；本地曼波中文用 `mambo-zh` |
| `rate` | string | 否 | edge-tts 语速，如 `+0%`；默认 `+0%` |
| `duration_s` | number | 是 | 目标总时长（秒）；决定字数预算与时长路由 |
| `route` | string | 是 | `template`（≤12s）或 `eac`（≥13s），由 R5 判定，见 §5 |
| `units_per_sec` | number | 否 | 语速基准，固定 `5.5`；写出来是为了让预算可追溯 |
| `scenes` | array | 是 | 镜头列表，4–6 个（R7）；首镜 `hook`、末镜 `outro` |
| `facts` | array | 否 | 事实清单，防编造数字（R4）；含数字的 `claim` 必须挂 http(s) 出处 |

### 单镜字段（`scenes[]`）

| 字段 | 类型 | 必填 | 含义 |
|---|---|---|---|
| `id` | string | 是 | 小写英文单词，全片唯一，**前 2 个字母不许重复**（`hook`/`chart`/`order`/`statement`/`event`/`outro`） |
| `role` | string | 是 | `hook` / `body` / `outro`，只用于结构校验（R7） |
| `visual_type` | string | 是 | `event`（有人有动作）/ `order`（流程步骤）/ `chart`（图表）/ `statement`（观点大字）。R6 靠它判节奏 |
| `duration_s` | number | 是 | 本镜时长；全片 `Σ duration_s` 必须等于顶层 `duration_s`（±0.3s，R7） |
| `narration` | string | 是 | 口播稿原文。**中文读法、带标点、零阿拉伯数字、零 `%`**（R4） |
| `visual` | string | 是 | 一句话说清这屏画什么：元素、位置、**画面上具体写哪几个标签** |
| `elements` | string | 否 | 上屏文字的枚举，逗号分隔，方便实现时逐个核对。每一项是画面上的一行字，**单行 ≤24 个汉字**（R8） |
| `motion` | object | 否 | 运镜：`{"type": "zoom-in" \| "pan-left" \| "pan-right" \| "pan-up" \| "pan-down", "amount": 0.01~0.5}`。**禁用 `zoom-out`**（R9） |

### 事实字段（`facts[]`）

| 字段 | 类型 | 必填 | 含义 |
|---|---|---|---|
| `claim` | string | 是 | 一条论断。**含数字的 claim 必须配 http(s) `source`**，否则 R4 打回 |
| `source` | string | 含数字时必填 | 出处，必须 `http://` 或 `https://` 开头 |
| `verified` | boolean | 否 | 是否人工核实过；`false` 的论断不许写进旁白 |

### 计数口径（R3/R4 共用）

**字数 = 汉字个数**（`[\u4e00-\u9fff]`），标点不算、阿拉伯数字不算、拉丁字母不算。
为什么：这样「写 `41.3%`」在字数上直接归零，规则互相咬合，不用额外写一条禁用符号的规则。

> `facts` 的链接是示例占位，实跑必须换成真实出处；`verified: false` 的数字不许进旁白。

自查：6 镜；汉字 171 个 ÷ 30s = **5.7 字/秒**（R3 区间 151.8~178.2，通过）；`Σ duration_s` = 30.0（R7 通过）；
首镜 `role=hook`、首字「昨」（R1 通过）；句间有承接——「那段演示」指代上一句、「它」连续指代、「是因为」给因果、末句「所以」收束，全片零「另外/此外」（R2b 通过）；
末镜有「你」和读者能做的动作「把清单丢进去跑一遍」，不是机构能力（R2c 通过）；
六镜视觉 `event → chart → order → statement → event → order`：无相邻同类，且没有相邻两镜同时是「没人」画面（`chart`/`statement`），R6 两条都通过；旁白零阿拉伯数字、零 `%`（R4 通过）；上屏每行 ≤24 汉字、运镜只有 `zoom-in` / `pan-right`（R8/R9 通过）。

## 3. 硬规则判定口径（H1–H6 ↔ R1–R10）

硬规则是拦住 2026-11 那次翻车的几道门；R1–R10 是它们的可执行落点（R2b/R2c 是 R2 的下半条，编号沿用不重排）。

| 硬规则 | 判定口径 | 规则编号 |
|---|---|---|
| **H1 首镜有主语**，不许以数字开头 | `scenes[0].narration` 首字符不得是阿拉伯数字、全角数字、`%`、`％`；首句必须出现「人/组织/产品」类主语（工程师、谷歌、它…） | **R1** |
| **H2 五问闸门** | 每镜至少答「谁 / 发生了什么」；全片必须有一镜答「为什么」（含「因为/是因为/之所以」）；末镜必须答「所以呢」（含「所以/以后」）**且落点落到读者身上**（R2c）；「什么时候」由首镜时间锚点或场景代入承担；**并且句与句之间要有承接**（R2b），不能拿「另外/此外」并列堆事实 | **R2 / R2b / R2c** |
| **H3 语速与数字** | 全片汉字数落在 `duration_s × 5.5` 的 ±8%；`narration` 禁用 `[0-9%％]` 与连续拉丁字母，须写中文读法；含数字的 `fact.claim` 必须有 http(s) `source` | **R3 / R4** |
| **H4 画面节奏与路由** | ① 相邻两镜 `visual_type` 不得相同；② 相邻两镜不得都是「没人」画面（`chart`/`statement`）；另每 3 镜至少 1 镜是 `event`/`order`；`duration_s ≤12` → `route=template`，`≥13` → `route=eac`（按 12 秒一刀切，不留灰区） | **R6 / R5** |
| **H5 上屏与运镜** | 上屏单行文字 ≤24 个汉字（1080 宽 / 40px 字号）；运镜只用 `zoom-in` / `pan`，**禁用 `zoom-out`** | **R8 / R9** |
| **H6 术语与口径** | 术语按受众定：「AI 不够酷」的读者懂 token / 上下文 / agent，别为「好懂」翻译掉。要卡的是**口径**——指代（「它」「总量」「四次」到底指什么）、数量级（分子分母、单位）、倍数与基数的对应关系 | **R10** |

> **放行口径（workflow Review-Storyboard）**：R2 的通过条件是 `verdict == clear`；`partly` 一律视为不通过。理由：partly 通常意味着"信息齐但表达有歧义"，观众能复述大意却答不准细节，这种片子上线后评论区会追问具体数字。

### 逐条规则（R1–R10）

| 编号 | 规则 | 失败信息与改法 |
|---|---|---|
| **R1** | 首镜第一句必须是「谁 + 何时 + 发生了什么」，且不以数字/百分号开头 | `first_scene_missing_subject`：首镜以 `41.3%` 开场 → 补主语与时间，数字挪到后文 |
| **R2** | 五问齐备：谁 / 什么时候 / 发生了什么 / 为什么 / 所以呢 | `five_questions_incomplete`：缺「为什么」或缺「所以呢」→ 加一句因果、补一句落点 |
| **R2b** | 句间承接（五问的下半条）：相邻两句必须有承接关系——因果（因为/所以）、转折（但/却）、递进（更/还）、指代（它/这/那段演示）；不许用「另外」「此外」「同时」「还有」把事实并排堆 | `no_through_line`：三句并列（`产量翻三倍。另外，团队只剩三个人。此外，成本降一半。`）→ 用一条因果串起来，或砍到只剩一条主证据 |
| **R2c** | 落点落到读者身上：末镜（`role=outro`）必须回答「这跟你有什么关系」——读者能不能用、会不会被影响、要不要做什么；**禁止只写机构能力、行业判断、厂商战略**。判定：末镜出现「你 / 你们」这类直指，或写明读者可执行的动作；两者都没有 = 不合格 | 反例 `所以模型文件公开后，公司能自己托管、自己改，不必被一家接口绑住。`（是机构能力，不是读者利益）→ 改成 `所以你要是写代码的，这个月就能拿它改自己的脚本，不用等公司采购。` |
| **R3** | 字数预算（写作期估算）：`Σ汉字（[一-龥]，标点/数字/字母不计） ÷ duration_s ∈ [5.06, 5.94]`（5.5 ±8%）。**这是写稿估值，不是成片时长承诺**——定稿前必须 TTS 实测，`duration_s` 按实测回填 | `narration_budget`：实际 5.2 → 按 `duration_s × 5.5` 补到 152~178 字（30s 例）；实测只有 4.65 字/秒 → 按实测重算时长，别信估值 |
| **R4** | 数字念法 + 数字出处：`narration` 不含阿拉伯数字、`%`、拉丁字母串；含数字的 `claim` 必须在 `facts[]` 里有 http(s) `source` | `narration_number_format`：`41.3%` 写成「百分之四十一点三」；`fact_unsourced`：`「41.3% 的团队」含数字但 facts[] 里没有 http 出处` → 补出处或删数字 |
| **R5** | 时长路由：`duration_s ≤12` → `route=template`；`≥13` → `route=eac`。没有中间档，也没有「打回」这一档 | `duration_route_mismatch`：13s 写成 `template` → 改 `eac`；想走模板就压到 12s 以内 |
| **R6** | 画面节奏（两条同时生效）：① 相邻两镜 `visual_type` 不得相同；② 相邻两镜不得都是「没人」画面（`chart`/`statement`）——`chart` 接 `statement` 虽然类型不同，但两屏都没有人，同样打回。另：任意连续 3 镜至少 1 镜 `event`/`order` | `visual_repeat` / `no_human_beat`：连排 `chart` → 中间插一镜 `event`（有人、有动作） |
| **R7** | 结构完整：`scenes` 4–6 个；首 `hook` 末 `outro`；`id` 唯一且前 2 字母不重复；`Σ duration_s` = 顶层 `duration_s`（±0.3s） | `structure_invalid`：补齐首尾镜、改重复 id、把镜头时长加总对上总时长 |
| **R8** | 上屏单行 ≤24 个汉字：`elements` 每一项（以及 `visual` 里要打在画面上的一行字）不超过 24 个汉字。1080 宽、40px 字号下一行约放 24 字；54px 下 33–38 字的长句会超出画幅被截断（EAC 不自动换行） | `caption_overflow`：一行 35 字 → 拆成两句，或把信息移到画面元素（表格/卡片），别缩字号硬塞 |
| **R9** | 运镜只用 `zoom-in` / `pan-left` / `pan-right` / `pan-up` / `pan-down`，**禁用 `zoom-out`**；`amount` 0.01~0.5 | `motion_zoom_out`：满画幅素材 zoom-out 会把画面缩出画框、镜尾露黑边（实测第 5 镜尾 0.6 秒全黑）→ 换 `zoom-in` 或同方向 `pan` |
| **R10** | 术语按受众定，卡的是口径：① 指代必须落地——「它」「总量」「四次」「第三次」指的是什么，句子里要能唯一确定；② 数字必须有分子分母和单位——涨了/降了说的是谁的哪个量；③ 倍数与基数必须对上——「翻三倍」的基数是哪个数。**不要卡术语本身**（读者懂 token / 上下文 / agent） | `unclear_reference` / `unclear_ratio`：`有四次` 是谁的四次、`总量` 是什么的总量、`第三次` 是第三次试验还是第三次调用 → 把主语、分子分母、基数在句子里写死；改不动说明这镜信息组织有问题，合并或删 |

为什么 R6 是两条同时生效：① 挡「同类翻页」——同一种画面连排，观众觉得在看 PPT；② 挡「类型不同但都没人」——`chart` 接 `statement`（或接 `compare`）类型确实不同，但两屏都没有人，连看两屏照样掉线。两条一起，才挡得住「数字密度高但没人」的片子；只写①会让读者误以为 `chart → statement` 合法。

为什么 R2b 要单列：五问查的是「信息齐不齐」，六句并列事实可以逐句答全，但观众记不住「为什么现在要关心它」；缺的是句与句之间的承接，主线就散了。R2b 脚本判不了（要读懂意思才判得出承接），由 Review/人工判：逐句标出它和上一句的承接词，标不出就改稿。启发式参考：全片「另外/此外/同时/还有」出现 ≥2 处，基本就是并列堆砌。

为什么 R2c 也要单列：五问问的是「这条片子讲了什么」，没问「关我什么事」。上一版末镜写「所以模型文件公开后，公司能自己托管、自己改」，那是机构能力；盲读的观众 so_what 答成「小团队 / 公司」，说明落点没落到人。最后一秒决定观众记不记得住，所以必须直指读者、或给出读者今天就能做的动作。R2c 同样由 Review/人工判（脚本判不了「读者利益」）。

为什么 R3 只是估算、不是承诺：Cursor 那期端到端实跑，176 汉字合成出来 37.84 秒（4.65 字/秒），比分镜按 5.5 写的 30s 慢了 26%，30 秒分镜出成 38 秒片子。5.5 只在写稿期用来控篇幅，实测区间是 4.6–5.6 字/秒；定稿前必须先跑 TTS 实测，用实测值回填 `duration_s`，再判 R3。

为什么 R8/R9 也是硬规则：这两条都是端到端实跑才暴露的——33–38 字的长句在 54px 下超出 1080 画幅被截断（EAC 不自动换行），降到 40px 才放得下；zoom-out 在满画幅素材上把画面缩出画框，镜尾露黑边（实测第 5 镜尾 0.6 秒全黑），换 zoom-in 就没了。不是审美偏好，是出片硬伤。

为什么 R10 卡口径、不卡术语：「AI 不够酷」的读者本身就关注 AI、天天在用 ChatGPT/Claude，token、上下文、agent 是他们的常识；为「好懂」把这些词翻译成大白话，只会显得外行、还占字数。OpenRouter 那条八轮盲读真正站得住的硬伤只有三类：「有四次」是谁的四次、「总量」是什么的总量、「第三次」是第三次试验还是第三次调用——这些跟受众无关，懂 token 的人一样会卡。其余「术语没解释」都是误判。
检查方法：把旁白给一个关注 AI 的人看，问「有没有哪个数字或指代你需要倒回去想？」，有就是硬伤；**不要**问「这个词你懂吗」。
反例：「有四次调用失败，总量降了，第三次才走对。」→ 正例：「谷歌那次把一个网页任务重试了四次，其中第三次才第一次点对按钮。」

实现对齐说明：`validate_storyboard.py` 按本节 R1–R10 与上面的计数口径实现（R2b/R2c/R8/R9/R10 目前由 Review 人工判）；脚本措辞与本节冲突时以本节为准，并在脚本里回写一行 note 说明差异。

为什么分两层：H 是给人看的写作规矩，R 是给校验脚本看的判定式。两者编号一一对应，改口径必须同时改文档与脚本。

## 4. 失败案例复盘（2026-11）

| 版本 | 时长 | 结果 | 直接原因 |
|---|---|---|---|
| 短版 | 9s | 数字密度高，观众看不懂 | 首镜「百分之四十一点三的活」——没有主语，不知道 41.3% 是谁的、哪一年的。今天会被 R1 直接拦 |
| 长版 | 30s | 论据更多、更难懂 | 一串并列数据（41.3%、六成、三倍），没有因果链，看完不知道「所以呢」 |
| 长版返工 | 30s → 41.4s | 超目标 38% | 按 4.5 字/秒写预算，实际 5.5；写 131 字只出 23.4 秒，反过来写满就超 |
| Cursor 那期（端到端） | 30s 分镜 → 37.84s 成片 | 超目标 26% | 176 汉字按实测 4.65 字/秒合成；分镜按 5.5 估，估少了四分之一。同批还踩到字幕溢出（54px 下 33–38 字被截断）和 zoom-out 镜尾黑边 |

### 三个病灶

1. **首镜缺主语。** 开场直接甩「百分之四十一点三的活」，观众不知道这数字属于谁、属于哪一年，只记住一个无主百分比。→ 修法：首镜先交代「谁 + 何时 + 发生了什么」，数字放第二镜。对应 R1。
2. **只有并列论据，没有因果链。** 全片在证明「数字很大」，没回答「为什么这样」「所以跟我有什么关系」。观众记住的是因果，不是并列。→ 修法：五问闸门 + 句间承接，缺「为什么」「所以呢」，或整段只是「另外/此外」堆事实，都直接打回。对应 R2 / R2b；末镜落点那一层见 R2c（上一版末镜只写「公司能自己托管、自己改」，盲读答成「小团队」，就是落点没落到人）。
3. **丢掉文章开头最天然的场面。** 原文第一段是「测试员把压缩包拖进 Audacity」——有真人、有动作、一秒看懂，天生是 `event` 镜；分镜却换成图表开场。→ 修法：先扫文章找「有人在做一件事」的段落，排成首镜 `event`；每 3 镜至少 1 镜有人有动作。对应 R6。

一句话教训：**观众看不懂，不是因为信息不够，是因为没人、没时间、没因果。**

## 5. 渲染协作（EAC 与 workflow 的边界）

- **模板线（`route=template`，≤12s，9s 兼容）**：`.claude/workflows/tutorial-video.yml` 全自动跑完——分镜 → TTS → 场景 HTML → HyperFrames 渲染 → `07_video.mp4`。
- **EAC 精品线（`route=eac`，≥13s）**：EAC 只以 **MCP 工具**形式存在（录制、时间线、调色、导出都得调工具）。workflow 里的子代理**没有这些工具**，只能产出 `08_eac_handoff.json`，由人在 EAC 里导入续做。
  - `08_eac_handoff.json` **由 `build_handoff.py` 从分镜生成，不手写**（见 §7）：镜号、`duration_s`、`narration`、`visual_type` / `visual` / `elements`、motion、facts 都在里面，`clips[].path` 默认 `pending` 等补素材。
  - workflow **不许**声称自己调过 EAC，也不许把未渲染的 handoff 当成品交付。为什么：自动调 EAC 需要人在环确认录屏窗口与素材许可，硬调只会产出空跑记录。
- **分界是 12 秒，不留灰区**：13s 起一律 EAC。为什么：两条线的成本和上限差一个量级，13–19s 这种「哪边都不合适」的时长只会两边都做不好，与其留一档打回，不如直接归到 EAC。
- 两条线共用同一份 `06_storyboard.json`，R1–R10 在分镜阶段校验一次，渲染前不重复判叙事。

## 6. 落地检查单

- [ ] 首镜 `hook`、首字不是数字，第一句说清「谁 + 何时 + 发生了什么」（R1）
- [ ] 五问都能在旁白里找到出处，末镜答「所以呢」（R2）
- [ ] 逐句标出它与上一句的承接词（因为/但/更/它…），标不出就改稿（R2b）
- [ ] 末镜念一遍，问「这跟我有什么关系」，答不上就改；末镜要有「你/你们」或读者能做的动作（R2c）
- [ ] 汉字数 = `duration_s × 5.5` ±8%（R3）
- [ ] 旁白零阿拉伯数字、零 `%`；英文名放 `elements`/`visual`（R4）
- [ ] 含数字的 `facts[].claim` 都有 http 出处，且 `verified`（R4）
- [ ] `route` 与 `duration_s` 匹配：≤12s → `template`，≥13s → `eac`（R5）
- [ ] 相邻两镜 `visual_type` 不同，且相邻两镜不得都是 `chart`/`statement`（没人画面），每 3 镜有人有动作（R6）
- [ ] 4–6 镜、首 hook 末 outro、id 前 2 字母不重复、时长相符（R7）

## 7. handoff 的生成与校验

`08_eac_handoff.json` 是**派生产物**，不是事实源：事实源只有 `06_storyboard.json`。handoff 由 `we-media-pipeline/scripts/build_handoff.py` 确定性生成——同一份分镜永远生成同一份 handoff（只有 `generated_at` 变），所以**不要手改**。→ 为什么：手写的 handoff 改稿后就对不上了，渲染出来还是旧镜头表，而且看不出来。

### 三条命令

```bash
# 1) 生成：默认写到分镜同目录的 08_eac_handoff.json
python we-media-pipeline/scripts/build_handoff.py 06_storyboard.json

# 试跑不想覆盖产物时指定路径
python we-media-pipeline/scripts/build_handoff.py 06_storyboard.json -o %TEMP%/08_eac_handoff.json

# 2) 校验：渲染前必跑，exit 0 才能进渲染
python we-media-pipeline/scripts/build_handoff.py 06_storyboard.json --verify

# 3) 自测：脚本内置夹具，改脚本后先跑它
python we-media-pipeline/scripts/build_handoff.py --selftest
```

退出码：`0` 生成成功 / 校验一致 / 自测通过；`1` 校验不一致；`2` 输入缺失或不合法（含 zoom-out 被拦）。→ 为什么：渲染流程只认 exit 0，别的都必须停下来修。

### motion 的优先级

- **分镜显式写 `motion.type` 的最优先**（`zoom-in` / `pan-left` / `pan-right` / `pan-up` / `pan-down`）。
- 没写就按 `visual_type` 映射：`event` → `zoom-in`、`order` → `pan-right`、`chart` → `zoom-in`、`statement` → `pan-left`。
- `motion.type` 写 `zoom-out` **直接报错**（exit 2，信息里点名第几镜、提 R9 已禁用）；`visual_type` 不在映射表里又没写 `motion.type`，同样报错，要你补 `motion.type` 或改 `visual_type`。→ 为什么：R9 是硬规则，生成期就拦，别等渲染出黑边才发现。

### sha256 是干什么的

handoff 里的 `storyboard_sha256` 是分镜文件的字节哈希。分镜改一个字，哈希就变，`--verify` 立刻报：

```
字段 storyboard_sha256 期望 <新哈希> 实际 <旧哈希>（分镜已改动，请重新生成 handoff）
```

这就是「**改稿即失效**」的实现方式：旧 handoff 不可能冒充新分镜被拿去渲染。逐镜还会比对 `motion` / `start` / `duration` / `caption` / `narration` / `vo`，不一致打印 `第 N 镜：字段 X 期望…实际…`，照它改分镜、重新生成即可。

另外：handoff 里每个 `clips[].path` 默认是 `pending`（素材待补），本仓库不做渲染；补素材、建项目、跑任务都在 EAC 的 MCP 工具里做（见 §5）。
